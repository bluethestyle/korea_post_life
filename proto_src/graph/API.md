# 관계망 자료(`graph.json`)와 관계 그래프 화면 (`site/proto/graph2.html`)

회사, 종형, 특약, 급부, 표준담보, 보장 대분류, 시장 동향을 노드로 잇고, 노드를 클릭하면 인접 노드를 펼쳐 가며 따라가는 화면이다(화면 머리의 이름은 "관계망 탐색", 공개 주소 `https://bluethestyle.github.io/korea_post_life/proto/graph2.html`). 2026-11-20에 만든 시안의 원본을 저장소로 옮긴 것이다.

같은 자료(`graph.json`)를 분석 화면(`site/proto/console4.html`)의 "관계 그래프" 탭도 읽는다(2026-11-23부터. 탭 이름은 2026-11-24에 관계 지도에서 바꿨다). 그 탭은 기준 종형 다섯과 그 비교 대상 종형을 오가므로, 자료는 화면에 올린 회사의 종형 전부를 싣고 화면이 세지 않아도 되는 요약(`summary`)을 함께 싣는다. 지금 배포된 탭은 보기 방식 셋(담보별 연결, 종형 구성, 시장 동향)과 검색, 실행 취소, 초기화 버튼을 두고, 노드를 클릭해 인접 열의 노드를 펼치거나 엣지를 클릭해 검수 상태와 급부역할 같은 관계 속성을 본다. 탭 코드(`proto_src/console4/tab6.js`)는 `summary`를 읽고 `edges2`, `kindLabels`, `ekindLabels`는 읽지 않는다. 이 탭은 별도 브랜치에서 재설계 중이므로, 머지되면 이 문단과 아래 "호환 규칙"의 2단계를 함께 고친다. 아래 절에서 `tab6.js`의 행 번호를 적은 곳은 2026-11-24 코드 기준이다.

## 다시 만드는 명령

```bash
# 1. 자료: data/snapshot(과 data/seed/hum_표준담보사전.jsonl, data/seed/표준담보_관계.jsonl,
#    data/proposals/표준담보_관계_두판독.jsonl)에서 graph.json
python proto_src/graph/build_data.py            # 출력 경로를 주면 거기에 쓴다(기본 proto_src/graph/graph.json)
# 2. 합치기: tpl.html + graph.json + proto_src/fonts/fonts_graph2.css → site/proto/graph2.html
python proto_src/graph/build.py                 # 출력 경로, --data <graph.json> 을 줄 수 있다
# 스냅샷의 다른 회사까지 실은 테스트용 자료(커밋하지 않는 자리에 쓴다)
python proto_src/graph/build_data.py out/graph_all.json --orgs all
python proto_src/graph/build.py out/graph2_all.html --data out/graph_all.json
```

- 싣는 종형: 화면에 올린 회사(`src/postlife/config.py`의 `SITE_ORGS`, 지금 `EPOST`, `HANWHALIFE`, `SAMSUNGFIRE`)의 종형 전부다. 2026-11-24 14:29 스냅샷에서 23개(우체국 8, 한화생명 8, 삼성화재 7)이다. 그 전에는 `WANT`로 고른 여섯(세 회사의 간편 종형 하나와 일반 종형 하나씩)만 실었고, `WANT`와 `pick_types`는 없앴다.
- 종형 노드의 차례는 화면의 종형 차례(`src/postlife/site/model.py`의 `Data.variant_order`: 우체국 먼저, 판매 중인 종형 먼저, 최근 개정판 먼저)다.
- 판매를 마친 종형(비교역할구분이 직전개정시연인 우체국 종형 셋)과 관문전용 종형도 싣는다. 요약의 `비교역할`과 `판매종료일`로 가른다.
- 급부가 없는 관문전용 종형(지금 한화생명 간편가입형 0년, 3년, 4년, 10년)은 종형 노드와 판매 엣지만 싣는다. 스냅샷에 있는 주계약 한 건도 싣지 않는다.
- `--orgs`: 주지 않으면 `SITE_ORGS`, `all`이면 스냅샷의 모든 회사, `EPOST,HANWHALIFE,SAMSUNGFIRE,MERITZ`처럼 쉼표로 이으면 그 회사들이다. 기본과 다른 묶음은 `proto_src/graph/graph.json`에 쓰지 않고 멈춘다(커밋되는 자료다). `scripts/export_app_data.py`와 같은 방식이다.
- 같은 입력이면 두 명령 모두 같은 바이트를 쓴다. `tests/test_graph_data.py`가 커밋된 `graph.json`과 `site/proto/graph2.html`이 커밋된 스냅샷으로 새로 만든 것과 같은지 본다(스냅샷이 더 새것이면 건너뛴다). 주간 스냅샷을 받은 뒤에는 위 두 명령으로 다시 만든다.
- `build.py`는 합친 파일에 외부 요청(src, href, url()의 바깥 주소, `<link>`, `@import`)이 있으면 쓰지 않고 멈춘다.
- 화면 일은 `tpl.html`만 고친다. `graph.json`과 `site/proto/graph2.html`은 빌드 산출물이라 손으로 고치지 않는다.
- 자료가 `build_data.py`가 아는 모양과 다르면 `graph.json`을 쓰지 않고 멈춘다(아래 "스키마 개정 1단계"의 빌드 중단 검사).

크기(2026-11-24 14:29 스냅샷, 2026-11-25 빌드): `graph.json` 3,381,467바이트(그 가운데 요약 31,132바이트, `edges2` 74,092바이트), `graph2.html` 3,946,525바이트. 2026-11-24 스키마 개정 1단계 직후(2026-11-23 스냅샷)에는 3,380,211바이트와 3,945,230바이트였다. 1단계 전에는 3,062,928바이트(요약 16,330바이트)와 3,627,947바이트였다(317,283바이트, 10.4% 늘었다). 여섯 종형만 실을 때는 1,186,479바이트와 1,751,470바이트였다. 바이트의 대부분은 급부 노드(약 1.93MB), 특약 노드(약 0.50MB), 포함 엣지(약 0.35MB), 매핑 엣지(약 0.22MB)다. 같은 상품 개정판의 종형들은 같은 특약과 급부를 종형마다 따로 노드로 싣는다(특약ID와 급부ID가 종형마다 다르다). 이름과 속성까지 같은 행을 한 번으로 치면 특약은 2,743개 가운데 1,036개, 급부는 6,615개 가운데 2,738개이고, 되풀이되는 노드와 포함 엣지가 약 1.67MB다. 5MB를 넘지 않아 형식은 그대로 두었다.

## graph.json 구조

```json
{"snapshot_at": "...", "kinds": [...], "ekinds": [...], "kindLabels": [...], "ekindLabels": [...],
 "nodes": [...], "edges": [...], "edges2": [...], "keys": [...], "summary": {...}, "표시명": {...}}
```

- `snapshot_at`: 스냅샷의 자료 시각(`data/snapshot/meta.json`). 화면 오른쪽 위 SNAPSHOT 자리에 나온다.
- `kinds`(노드 종류, 번호 순): 0 회사, 1 종형, 2 특약, 3 급부, 4 표준담보, 5 보장 대분류, 6 시장 동향. 2026-11-24에 보장분야, 소식에서 바꿨다. 스키마 개정 1단계(2026-11-24)부터 이 글자는 바꾸지 않는 자료 이름이고, 화면에 보일 이름은 `kindLabels`다(지금은 둘이 같다).
- `ekinds`(엣지 종류, 번호 순): 0 판매(회사→종형), 1 포함(종형→특약, 특약→급부), 2 매핑(급부→표준담보, `hum_담보매핑`의 검토상태가 자동확정, 승인, 수정인 행), 3 분류(표준담보→보장 대분류), 4 담보 관계(좁은 표준담보→넓은 표준담보), 5 발표(회사→시장 동향), 그리고 1단계에서 끝에 붙인 6 보유, 7 결합제약, 8 개정, 9 언급 담보, 10 언급 상품(아래 "스키마 개정 1단계"). 0~5는 2026-11-24에 해당, 속함, 관계, 일으킴에서 바꾼 글자 그대로다. `build_data.py` 안에서는 예전 이름을 키로 쓰고 내보낼 때만 바꾼다(`src/postlife/site/terms.py`의 `GRAPH_NODE_KIND`, `GRAPH_EDGE_KIND`).
- `kindLabels`, `ekindLabels`: `kinds`, `ekinds`와 같은 차례의 화면 이름(`terms.py`의 `GRAPH_KIND_LABEL`, `GRAPH_EDGE_LABEL`). 자료 이름과 다른 것은 7번 결합제약의 "특약 부가 조건"(용어 대조표 68행)뿐이다.
- `nodes`: 노드 하나가 `[ID, 종류 번호, 이름, 기관코드 또는 null, 속성]` 배열이다. ID는 스냅샷의 종형ID, 특약ID, 급부ID, 표준담보ID, 동향ID를 그대로 쓰고, 회사는 `ORG:<기관코드>`, 보장 대분류는 `CAT:<보장대분류>`이다(ID 규칙은 바꾸지 않았다).
- `edges`: 엣지 하나가 `[출발 노드 번호, 도착 노드 번호, 종류 번호, 속성]` 배열이다. 노드 번호는 `nodes` 배열의 자리(0부터)다. 엣지 종류 0~5만 싣는다.
- `edges2`: `edges`와 같은 형식이고 1단계에서 더한 엣지 종류 6~10만 싣는다. 지금 화면 둘은 읽지 않는다.
- `keys`: 속성 이름 목록. 노드와 엣지의 속성은 `{"<keys 의 번호>": 값}` 꼴로 줄여 담았다. 값이 없는 속성은 넣지 않는다. 1단계 전의 37개(0 `기관코드`부터 36 `발표일`까지)는 번호가 그대로이고, 1단계에서 더한 속성 이름은 37번부터다. 화면은 번호를 글자로 고정하지 말고 `keys`로 이름을 되돌려 읽는다.
- `summary`: 화면이 세지 않아도 되는 요약(아래 "요약"). 2026-11-23에 더했다.
- `표시명`: 키로 남긴 값의 화면 이름(아래 "화면 용어와 표시명"). 2026-11-24에 더했다.

노드와 엣지의 꼴, ID 규칙, 속성은 종형을 넓힐 때(2026-11-23) 바꾸지 않았다. 노드 번호는 싣는 종형이 늘어 바뀌었으므로, 노드 번호를 글자로 고정해 두지 말고 ID로 찾는다.

- 종형 노드의 이름(2026-11-24): 공시상품명(앞의 "무배당 "을 뗀다) 뒤에 종형명을 붙이되, 종형명이 이름에 두 번 들지 않게 한다. 공시상품명이 종형명으로 끝나면(띄어쓰기 무시) 공시상품명만 쓰고, 공시상품명의 끝 낱말이 종형명의 앞부분이면 종형명에서 그 앞부분을 뗀 나머지만 붙인다(`build_data.type_label`). 이름이 바뀐 종형은 12개다(우체국 6, 삼성화재 6).
- 특약 노드의 `보장대분류`는 표준담보 노드의 `보장대분류`(글자 하나)와 이름은 같고 값이 목록이다. 노드 종류로 가려 읽는다. 매핑 검수 대기가 확정되면 바뀐다.
- 특약 노드에 `가입금액연동`이 없다고 "연동 없음"으로 읽지 않는다. 우체국 선택특약 가운데 최대연동 행이 없는 것이 공시에 없는지 추출하지 않았는지는 확인하지 않았고, 한화생명과 삼성화재는 결합제약이 0행이다.

엣지 종류별 속성(0~5): 포함(종형→특약)은 담보구분, 갱신. 포함(특약→급부)은 급부역할. 매핑은 검토상태(화면 이름 "검수 상태". 속성 이름은 `keys`에 그대로 있고 `표시명`으로 바꿔 보인다), 매핑확률(숫자. 1단계 전에는 빈값을 "교차 확인" 글자로 채웠고 1단계부터는 빈값이면 넣지 않는다), **확정방식**(검토상태가 자동확정인 엣지에만. 매핑확률이 있으면 확률 산정 모델, 없으면 교차 검증. 지금 2,243건과 2,036건). 분류는 보장중분류. 담보 관계는 관계, 확신_gemini, 확신_claude. 발표는 분류유형, 발표일. 판매는 없음. 속성 이름과 값은 시트 값을 그대로 옮긴 것이다.

- 담보 관계 엣지는 1단계부터 시드(`data/seed/표준담보_관계.jsonl`)의 넓은담보ID, 좁은담보ID로 만들고, 확신 값만 이중 추출 파일(`data/proposals/표준담보_관계_두판독.jsonl`)에서 (관계, 넓은담보, 좁은담보)로 찾아 붙인다. 두 파일의 행 차례가 같아 엣지 차례와 값은 1단계 전과 같다. 방향은 그대로 좁은 담보→넓은 담보다(아래 호환 규칙).

화면에 올린 회사 밖의 회사(지금 스냅샷의 메리츠화재 등)는 시장 동향의 회사 노드로만 나온다(발표 엣지뿐). 그 회사의 종형, 특약, 급부, 매핑은 싣지 않는다(`src/postlife/site/orgs.py`의 `filter_tables`가 스냅샷을 읽는 단계에서 제외한다).

- 비교역할, 미연결사유, 매핑상태, 선별상태, 속성 이름을 화면에 낼 때는 `표시명`을 거친다(아래 절). 노드 종류와 엣지 종류의 이름은 `kindLabels`, `ekindLabels`로 보인다(지금 화면은 `kinds`, `ekinds`를 그대로 보이고, 0~6과 0~5는 두 배열의 글자가 같다).

| 1단계(이 자료) | 지금 화면 둘은 바꿀 것이 없다. 새 노드 속성은 상세 패널의 속성 표에 더 나올 뿐이고, `edges2`, `kindLabels`, `ekindLabels`, `summary.특약계보`는 읽는 곳이 없다. `ekinds`에 붙은 6~10은 tpl.html의 필터 팝업에 엣지가 없는 버튼 다섯으로 나온다. 매핑확률이 빈 엣지는 tpl.html이 "교차"로 적는다(숫자가 아니면 그렇게 적는다). 2026-11-24에 두 화면을 브라우저로 열어 콘솔 오류 0, 노드와 엣지 요소 수가 1단계 전과 같음을 확인했다 | `nodes`의 차례와 형식, 노드 종류 0~6, `edges`(종류 0~5)의 차례, 양 끝, 종류, `ekinds` 0~5의 차례와 글자, `keys`의 기존 번호(0~36), `summary`의 기존 키 |
| 2단계(화면, Antigravity) | 새 화면은 종류를 번호 대신 `kinds`, `ekinds`의 이름으로 찾고, 보일 때는 `kindLabels`, `ekindLabels`, `표시명`을 거친다. `edges`와 `edges2`를 함께 색인에 넣는다. 보유는 보유 엣지에서 읽고 경로 색인으로 세지 않는다. 판정과 관련 담보 표시는 cover.json(`App.cover`)에서 읽는다 | 담보 관계의 방향(좁은 담보→넓은 담보). 새 화면은 방향을 상수 하나로 읽게 해 3단계에서 자료와 함께 바꿀 수 있게 한다 |
| 3단계(정리, Claude) | 2단계 머지 뒤에 한다: `edges2`를 `edges`로 합치고, 노드 속성과 같은 엣지 속성(포함의 담보구분과 갱신, 분류의 보장중분류, 발표의 분류유형과 발표일)을 빼고, 담보 관계 방향을 넓은 담보→좁은 담보로 바꾼다. graph2를 계속 둔다면 tpl.html의 `eShort`에 새 종류를 먼저 넣는다 | |

담보 관계 방향을 1단계에서 바꾸지 않은 이유: 재설계 검토 문서는 1단계에 바꾸자고 했지만, 지금 두 화면이 방향을 보이는 데 쓴다. tab6.js는 엣지 상세의 제목(`출발 -> 도착`, 1629행)과 출발 노드, 도착 노드 행(1636~1641행), 엣지 선택을 풀 때 돌아갈 노드(같은 열 엣지는 출발 노드, 802행과 2133행)에 쓰고, tpl.html은 화살표 머리(601행), 관계 목록의 →, ←, ↔ 표시(638~639행), 엣지 상세의 제목과 출발, 도착 버튼(697~700행)에 쓴다. 바꾸면 오류는 없지만 보이는 방향이 뒤집히므로 화면을 고치는 2단계와 묶어 3단계에서 바꾼다.

### 화면이 지킬 것

- 판정(우위, 열위, 단순 비교 불가, 관련 담보로 보장, 우체국 미보유, 타사 미보유, 검수 대기)은 graph.json에 없다. 담보 비교 탭과 같은 cover.json을 읽는다(`App.cover.peerVerdicts`, 우체국 셀 `rows[k][1][0]`의 `c`). 같은 판정을 두 파일에 두지 않는다.
- 속성이 없다는 것을 "해당 없음", "연동 없음", "검수 완료"로 보이지 않는다. 원천에 값이 있을 때만 싣는다.
- 화면이 수를 새로 세지 않는다. 보유 여부와 급부 수는 보유 엣지, 담보 수는 `summary`, 개정 내역 수는 개정 엣지에서 읽는다. 화면은 엣지를 따라가는 탐색과 집합 연산만 한다.

```js
const RAW = JSON.parse(document.getElementById('gdata').textContent);
const EK = Object.fromEntries(RAW.ekinds.map((n, i) => [n, i]));            // 종류는 이름으로 찾는다
const dec = p => Object.fromEntries(Object.entries(p).map(([k, v]) => [RAW.keys[+k], v]));
const all = RAW.edges.concat(RAW.edges2 || []);                                // 2단계부터 함께 색인한다
const held = all.filter(e => e[2] === EK['보유'])                             // 종형 → 표준담보
  .map(([s, t, , p]) => ({ type: RAW.nodes[s][0], std: RAW.nodes[t][0], ...dec(p) }));
// held[0] = { type: 'EPOST_P500129_8dba92', std: 'STD_CA_DX_GENERAL', 급부수: 1, 특약수: 1, 대표급부ID: 'EPOST_..._B7ac2beae' }
const label = k => RAW.ekindLabels[k];                                         // 7 → '특약 부가 조건'
const lineage = RAW.summary['특약계보']['EPOST'];                              // {특약계보키: [종형 노드 번호]}
```

## 분석 화면의 키와 같은가

- 종형ID: 같은 글자다. sales.json의 `종형` 키, `기준종형[].종형ID`, `기준별` 키와 `맞붙는종형` 값, cover.json의 `b` 키와 `cols`는 모두 graph.json의 종형 노드 ID(`summary.종형`의 키)다. 이어 주는 표는 싣지 않는다.
- 표준담보ID: 같은 글자다. cover.json `rows`의 첫 칸은 표준담보 노드 ID다. 다만 graph.json은 사용여부가 참인 표준담보만 노드로 싣고 sales.json의 `표준담보`는 사용여부가 거짓인 담보(지금 `STD_HT_DX_CARDIO`)도 싣는다. 그 담보는 graph.json에 노드가 없다.
- 종형의 범위: graph.json은 화면에 올린 회사의 종형 23개를, sales.json의 `종형`은 20개를 싣는다(2026-11-24 14:29 스냅샷). graph.json에만 있는 셋은 우체국 직전 개정 상품(비교역할 `직전개정시연`) 종형이다. 한화생명의 인수기준만 수집(`관문전용`) 종형 넷은 두 자료에 모두 있다.
- 위 셋은 자료 시각이 같을 때 `tests/test_graph_data.py`가 확인한다.

## 화면이 자료를 읽는 자리 (graph2.html)

- `tpl.html`의 `<script type="application/json" id="gdata">__DATA__</script>`에 `build.py`가 graph.json을 넣는다(`</`는 `<\/`로 바꿔 넣는다).
- 스크립트 첫머리에서 `RAW=JSON.parse(#gdata)`로 읽고, `KIND=RAW.kinds`, `EK=RAW.ekinds`, `KEYS=RAW.keys`로 받은 뒤 `N`(노드), `E`(엣지)로 풀어 쓴다. 속성은 `dec()`가 `keys`로 이름을 되돌린다. 관계 그래프 화면은 `summary`, `edges2`, `kindLabels`, `ekindLabels`를 읽지 않는다. `EK`에는 1단계에서 6~10이 붙었지만 엣지가 `RAW.edges`에 없어 관계 목록(`relList`)과 상세 패널에 나오지 않는다. 다만 필터 팝업(726행)은 `EK` 전부로 버튼을 만들므로 엣지 종류 버튼이 11개가 되고(새 다섯 버튼은 걸리는 엣지가 없다) 724행의 수도 "11/11"로 나온다. 오류는 없다.
- 회사 색과 배지는 `MAIN=['EPOST','HANWHALIFE','SAMSUNGFIRE']`와 CSS 변수 `--o-<기관코드>`로 정하고, 나머지 회사는 `--o-OTHER`로 그린다.
- 시작 버튼은 `MAIN`의 회사 셋과 `STARTS`(표준담보 이름 목록)다. 시작 카드 머리의 노드 수는 `N.length`다(2026-11-23 전에는 3,744를 글자로 고정해 두었다).
- 글꼴은 `<style>/*__FONTS__*/</style>` 자리에 `proto_src/fonts/fonts_graph2.css`가 들어간다(PLDisplay, PLBody, PLNum, PLWide).
- 2026-11-23 스냅샷(노드 9,509, 엣지 13,802)에서 380px, 1280px 폭으로 열어 시작 버튼 여덟을 클릭해 인접 노드를 펼치고, 한화생명 일반가입형에서 같은 회사의 다른 종형으로 넘어가 보았다. 콘솔 오류와 외부 요청은 없었다.

## 화면 용어와 표시명 (2026-11-24 추가)

분석 화면의 규약(`proto_src/console4/API.md` 맨 끝 "화면 용어와 표시명")과 같은 방식이다. 화면 코드가 키로 쓰는 시트 값과 속성 이름은 바꾸지 않고, 화면에 보일 이름을 `표시명`(평면 맵 `{키 값: 화면 이름}`)으로 싣는다.

| 구분 | 키 → 화면 이름 | 키로 쓰는 곳 |
| --- | --- | --- |
| 비교역할 | 관문전용 → 인수기준만 수집, 직전개정시연 → 직전 개정 상품 | `summary.종형[].비교역할`(시트 허용값) |
| 미연결사유, 매핑상태 | 대기 → 매핑 검수 대기(대조표 111행, 1단계에서 더함), 대상외 → 매핑 대상 외 | `summary.종형[].미연결사유`의 키와 급부 노드의 `매핑상태` 값(`hum_담보매핑` 검토상태 값). 오류, 사전밖, 매핑없음은 대조표에 행이 없어 싣지 않았다 |
| 선별상태 | passed → 통과, below → 통과 기준 미달, undecided → 확률 산정 결과 없음(1단계에서 더함) | 시장 동향 노드의 `선별상태`(`weekly.news_state`의 값) |
| 속성 이름 | 검토상태 → 검수 상태, 종료 → 삭제(대조표 136행, 1단계에서 더함), 판정확률 → 확률 산정 결과(2026-11-25) | `keys`의 속성 이름(매핑 엣지의 검토상태, 개정 엣지의 종료, 시장 동향 노드의 판정확률) |

노드 종류와 엣지 종류는 표시명에 싣지 않는다. 0~6과 0~5는 2026-11-24에 `kinds`, `ekinds`의 이름 자체를 화면 이름으로 바꿨다: 보장분야 → 보장 대분류, 소식 → 시장 동향, 해당 → 매핑, 속함 → 분류, 관계 → 담보 관계, 일으킴 → 발표. 1단계부터 이 글자는 자료 이름으로 고정하고 화면 이름은 `kindLabels`, `ekindLabels`로 싣는다(결합제약 → 특약 부가 조건). 확정방식(확률 산정 모델, 교차 검증), 기관구분, 업권, 제약유형의 값은 화면 이름 그대로라 표시명에 싣지 않았다. 짧은 표기(열 이름 자리의 동향, 관계, 대분류)는 자료에 싣지 않고 화면 문구 표에서 정한다. 화면 코드에 예전 이름을 기본값으로 적어 둔 목록(분석 화면 `tab6.js`의 `kinds`, `ekinds` 기본 목록, 이 화면 `tpl.html`의 `eShort`)은 자료의 이름과 같게 맞춘다.

```js
const glabel = v => (RAW['표시명'] && RAW['표시명'][v]) || v;
glabel(vs['비교역할']);   // '관문전용' → '인수기준만 수집'
glabel('대상외');         // '매핑 대상 외'
glabel('대기');           // '매핑 검수 대기'
glabel('passed');         // '통과'
glabel('검토상태');       // 속성 이름 표시 '검수 상태'
RAW.kinds[5];             // '보장 대분류'
RAW.ekinds[2];            // '매핑'
RAW.ekinds[7];            // '결합제약'(자료 이름). 화면에는 RAW.ekindLabels[7] '특약 부가 조건'
```

규약 테스트: `tests/test_display_names.py`(표시명과 종류 이름), `tests/test_graph_data.py`.
