# 관계망 자료(`graph.json`)와 탐색 시안 2 (`site/proto/graph2.html`)

회사, 종형, 특약, 급부, 표준담보, 보장 대분류, 시장 동향을 노드로 잇고, 노드를 클릭하면 이웃을 펼쳐 가며 따라가는 화면이다. 2026-11-20에 만든 시안의 원본을 저장소로 옮긴 것이다.

같은 자료(`graph.json`)를 시안 4(`site/proto/console4.html`)의 "관계 그래프" 탭도 읽는다(2026-11-23부터. 탭 이름은 2026-11-24에 관계 지도에서 바꿨다). 그 탭은 기준 종형 다섯과 그 비교 대상 종형을 오가므로, 자료는 화면에 올린 회사의 종형 전부를 싣고 화면이 세지 않아도 되는 요약(`summary`)을 함께 싣는다.

## 다시 만드는 명령

```bash
# 1. 자료: data/snapshot(과 data/seed/hum_표준담보사전.jsonl, data/proposals/표준담보_관계_두판독.jsonl)에서 graph.json
python proto_src/graph/build_data.py            # 출력 경로를 주면 거기에 쓴다(기본 proto_src/graph/graph.json)
# 2. 합치기: tpl.html + graph.json + proto_src/fonts/fonts_graph2.css → site/proto/graph2.html
python proto_src/graph/build.py                 # 출력 경로, --data <graph.json> 을 줄 수 있다
# 사본의 다른 회사까지 실은 시험용 자료(커밋하지 않는 자리에 쓴다)
python proto_src/graph/build_data.py out/graph_all.json --orgs all
python proto_src/graph/build.py out/graph2_all.html --data out/graph_all.json
```

- 싣는 종형: 화면에 올린 회사(`src/postlife/config.py`의 `SITE_ORGS`, 지금 `EPOST`, `HANWHALIFE`, `SAMSUNGFIRE`)의 종형 전부다. 2026-11-23 사본에서 23개(우체국 8, 한화생명 8, 삼성화재 7)이다. 그 전에는 `WANT`로 고른 여섯(세 회사의 간편 종형 하나와 일반 종형 하나씩)만 실었고, `WANT`와 `pick_types`는 없앴다.
- 종형 노드의 차례는 화면의 종형 차례(`src/postlife/site/model.py`의 `Data.variant_order`: 우체국 먼저, 판매 중인 종형 먼저, 최근 개정판 먼저)다.
- 판매를 마친 종형(비교역할구분이 직전개정시연인 우체국 종형 셋)과 관문전용 종형도 싣는다. 요약의 `비교역할`과 `판매종료일`로 가른다.
- 급부가 없는 관문전용 종형(지금 한화생명 간편가입형 0년, 3년, 4년, 10년)은 종형 노드와 판매 엣지만 싣는다. 스냅샷에 있는 주계약 한 건도 싣지 않는다.
- `--orgs`: 주지 않으면 `SITE_ORGS`, `all`이면 사본의 모든 회사, `EPOST,HANWHALIFE,SAMSUNGFIRE,MERITZ`처럼 쉼표로 이으면 그 회사들이다. 기본과 다른 묶음은 `proto_src/graph/graph.json`에 쓰지 않고 멈춘다(커밋되는 자료다). `scripts/export_app_data.py`와 같은 방식이다.
- 같은 입력이면 두 명령 모두 같은 바이트를 쓴다. `tests/test_graph_data.py`가 커밋된 `graph.json`과 `site/proto/graph2.html`이 커밋된 사본으로 새로 만든 것과 같은지 본다(사본이 더 새것이면 건너뛴다). 주간 사본을 받은 뒤에는 위 두 명령으로 다시 만든다.
- `build.py`는 합친 파일에 외부 요청(src, href, url()의 바깥 주소, `<link>`, `@import`)이 있으면 쓰지 않고 멈춘다.
- 화면 일은 `tpl.html`만 고친다. `graph.json`과 `site/proto/graph2.html`은 생성물이라 손으로 고치지 않는다.

크기(2026-11-23 스냅샷, 2026-11-24에 종류 이름을 바꾸고 표시명을 더한 뒤): `graph.json` 3,062,928바이트(그 가운데 요약 16,330바이트), `graph2.html` 3,627,947바이트. 여섯 종형만 실을 때는 1,186,479바이트와 1,751,470바이트였다. 바이트의 대부분은 급부 노드(약 1.93MB), 특약 노드(약 0.50MB), 포함 엣지(약 0.35MB), 매핑 엣지(약 0.22MB)다. 같은 상품 개정판의 종형들은 같은 특약과 급부를 종형마다 따로 노드로 싣는다(특약ID와 급부ID가 종형마다 다르다). 이름과 속성까지 같은 행을 한 번으로 치면 특약은 2,743개 가운데 1,036개, 급부는 6,615개 가운데 2,738개이고, 되풀이되는 노드와 포함 엣지가 약 1.67MB다. 5MB를 넘지 않아 형식은 그대로 두었다.

## graph.json 구조

```json
{"snapshot_at": "...", "kinds": [...], "ekinds": [...], "nodes": [...], "edges": [...], "keys": [...], "summary": {...}, "표시명": {...}}
```

- `snapshot_at`: 사본의 자료 시각(`data/snapshot/meta.json`). 화면 오른쪽 위 SNAPSHOT 자리에 나온다.
- `kinds`(노드 종류, 번호 순): 0 회사, 1 종형, 2 특약, 3 급부, 4 표준담보, 5 보장 대분류, 6 시장 동향. 이름이 곧 화면 이름이다(2026-11-24에 보장분야, 소식에서 바꿨다. 화면은 종류를 번호로 다루므로 번호는 그대로다)
- `ekinds`(엣지 종류, 번호 순): 0 판매(회사→종형), 1 포함(종형→특약, 특약→급부), 2 매핑(급부→표준담보, `hum_담보매핑`의 검토상태가 자동확정, 승인, 수정인 행), 3 분류(표준담보→보장 대분류), 4 담보 관계(좁은 표준담보→넓은 표준담보), 5 발표(회사→시장 동향). 2026-11-24에 해당, 속함, 관계, 일으킴에서 바꿨다. `build_data.py` 안에서는 예전 이름을 키로 쓰고 내보낼 때만 바꾼다(`src/postlife/site/terms.py`의 `GRAPH_NODE_KIND`, `GRAPH_EDGE_KIND`)
- `nodes`: 노드 하나가 `[ID, 종류 번호, 이름, 기관코드 또는 null, 속성]` 배열이다. ID는 스냅샷의 종형ID, 특약ID, 급부ID, 표준담보ID, 동향ID를 그대로 쓰고, 회사는 `ORG:<기관코드>`, 보장 대분류는 `CAT:<보장대분류>`이다(ID 규칙은 바꾸지 않았다).
- `edges`: 엣지 하나가 `[출발 노드 번호, 도착 노드 번호, 종류 번호, 속성]` 배열이다. 노드 번호는 `nodes` 배열의 자리(0부터)다.
- `keys`: 속성 이름 목록. 노드와 엣지의 속성은 `{"<keys 의 번호>": 값}` 꼴로 줄여 담았다. 값이 없는 속성은 넣지 않는다.
- `summary`: 화면이 세지 않아도 되는 요약(아래 "요약"). 2026-11-23에 더했다.
- `표시명`: 키로 남긴 값의 화면 이름(아래 "화면 용어와 표시명"). 2026-11-24에 더했다.

노드와 엣지의 꼴, ID 규칙, 속성은 종형을 넓힐 때(2026-11-23) 바꾸지 않았다. 노드 번호는 싣는 종형이 늘어 바뀌었으므로, 노드 번호를 글자로 박아 두지 말고 ID로 찾는다.

노드 종류별 속성

| 종류 | 속성 |
| --- | --- |
| 회사 | 기관코드 |
| 종형 | 공시상품명, 종형명, 간편고지, 갱신유형, 갱신주기년, 심사유형, 환급유형, 적용시작일 |
| 특약 | 담보구분, 갱신여부(갱신/비갱신), 갱신주기년, 최소가입금액만원, 최대가입금액만원 |
| 급부 | 기준지급액(예: "1000만원", "가입금액의 20%"), 기준가입금액만원, 면책일수, 감액(예: "12개월 이내 50%", 없으면 "없음"), 지급횟수제한, 근거("<근거문서종류> <쪽>쪽") |
| 표준담보 | 보장대분류, 보장중분류, 급부유형, 비교기준단위만원 |
| 보장 대분류 | 없음 |
| 시장 동향 | 핵심요약, 분류유형, 발표일자, 매체명, 출처URL, 판정확률 (이름은 핵심요약 앞 40자) |

엣지 종류별 속성: 포함(종형→특약)은 담보구분, 갱신. 포함(특약→급부)은 급부역할. 매핑은 검토상태(화면 이름 "검수 상태". 속성 이름은 `keys`에 그대로 있고 `표시명`으로 바꿔 보인다), 매핑확률(없으면 "교차 확인"). 분류는 보장중분류. 담보 관계는 관계, 확신_gemini, 확신_claude. 발표는 분류유형, 발표일. 판매는 없음. 속성 이름과 값은 시트 값을 그대로 옮긴 것이다.

화면에 올린 회사 밖의 회사(지금 스냅샷의 메리츠화재 등)는 시장 동향의 회사 노드로만 나온다(발표 엣지뿐). 그 회사의 종형, 특약, 급부, 매핑은 싣지 않는다(`src/postlife/site/orgs.py`의 `filter_tables`가 스냅샷을 읽는 단계에서 제외한다).

## 요약(`summary`)

```json
"summary": {
  "회사": ["EPOST", "HANWHALIFE", "SAMSUNGFIRE"],
  "종형": {
    "EPOST_P500130_099c2b": {"노드": 2, "심사유형": "간편심사", "비교역할": "정밀비교", "특약수": 22, "급부수": 49,
                             "표준담보": [9384, 9395, ...], "보장분야별": {"CAT:암보장": 8, "CAT:뇌혈관보장": 6, ...},
                             "미연결급부": 5, "미연결사유": {"대상외": 5}},
    "EPOST_P500108_19aa78": {"노드": 8, "비교역할": "직전개정시연", "판매종료일": "2026-06-16", ...}
  },
  "표준담보별종형": {"STD_CA_DX_GENERAL": [1, 2, 3, ...], "STD_CA_DX_HIGH": [5], ...},
  "기준종형": ["EPOST_P500129_8dba92", ...],
  "맞붙는종형": {"EPOST_P500129_8dba92": ["HANWHALIFE_2597_3c2dbb", "SAMSUNGFIRE_ZPB357050_9bf87f"], ...}
}
```

읽는 규칙: 열쇠는 노드 ID(종형ID, 표준담보ID, `CAT:<보장대분류>`)이고, 목록의 값은 노드 번호(`nodes`의 자리)다. 단 `기준종형`과 `맞붙는종형`의 값은 sales.json과 같은 값이어야 하므로 종형ID다. 값이 없는 칸(판매종료일 따위)은 넣지 않는다.

| 이름 | 뜻 |
| --- | --- |
| `회사` | 실은 회사의 기관코드. 종형 차례에서 처음 나온 차례다 |
| `종형` | 실은 종형 전부. 열쇠는 종형ID, 차례는 종형 노드 차례(화면의 종형 차례)다 |
| `종형[].노드` | 그 종형 노드의 번호 |
| `종형[].심사유형` | `sys_상품종형`의 심사유형 그대로(일반심사, 간편심사) |
| `종형[].비교역할` | `sys_상품종형`의 비교역할구분 그대로(정밀비교, 관문전용, 직전개정시연). 담보 비교와 영업 인사이트는 정밀비교 종형만 본다 |
| `종형[].판매종료일` | 판매를 마친 종형에만 있다 |
| `종형[].특약수`, `급부수` | 그 종형에서 포함 엣지를 따라 닿는 특약 노드와 급부 노드의 수 |
| `종형[].표준담보` | 그 종형의 급부에서 매핑 엣지로 닿는 표준담보 노드 번호(겹치지 않게, 오름차순). 매핑 엣지는 검토상태가 자동확정, 승인, 수정인 매핑만 만든다. 시안 4의 담보 비교(`compare.collect`의 확정 담보)가 그 종형에 있다고 보는 표준담보와 같다(테스트로 확인한다) |
| `종형[].보장분야별` | 위 표준담보를 보장 대분류(분류 엣지)로 나눈 수. 열쇠 이름 `보장분야별`은 그대로다. 열쇠는 보장 대분류 노드 ID, 차례는 보장 대분류 노드 차례, 0인 분류는 넣지 않는다. 합은 `표준담보`의 길이다 |
| `종형[].미연결급부` | 매핑 엣지가 없는 급부의 수(표준담보로 이어지지 못한 급부). `급부수`에서 표준담보로 이어진 급부 수를 뺀 값이다 |
| `종형[].미연결사유` | `미연결급부`를 사유로 나눈 수. 차례는 대기, 오류, 대상외, 사전밖, 매핑없음이고 0인 사유는 넣지 않는다. 합은 `미연결급부`다. 사유는 키다(`대상외`의 화면 이름은 `표시명`의 "매핑 대상 외") |
| `표준담보별종형` | 표준담보 노드마다 그 담보를 가진 종형의 노드 번호(오름차순). 표준담보 노드 전부를 노드 차례로 싣고, 가진 종형이 없으면 빈 목록이다 |
| `기준종형` | 기준 종형(판매 중인 우체국 정밀비교 종형). sales.json의 `기준종형` 차례와 같다 |
| `맞붙는종형` | 기준 종형마다 다른 회사에서 하나씩 선택한 비교 대상 종형. sales.json의 `기준별[].맞붙는종형`과 같은 값이고, 여기서 다시 선택하지 않고 같은 함수(`src/postlife/site/sales.py`의 `_Ctx.bases`와 `_Ctx.default_peers`, 그 안은 `compare.peers`)에서 얻는다 |

미연결사유의 뜻

| 사유 | 뜻 |
| --- | --- |
| 대기 | 매핑 검수 대기(`hum_담보매핑`의 검토상태가 대기). 담당자가 정하면 연결될 수 있다. 매핑 엣지는 만들지 않는다 |
| 오류 | 검토상태가 오류인 매핑 |
| 대상외 | 표준담보 사전 범위 밖의 급부(검토상태가 대상외). 빠진 담보가 아니다 |
| 사전밖 | 검토상태는 자동확정, 승인, 수정인데 확정표준담보ID가 비었거나 사전(사용여부가 참인 행)에 없다 |
| 매핑없음 | 그 급부의 `hum_담보매핑` 행이 없다 |

2026-11-23 스냅샷에서는 미연결 급부가 2,336건(대상외 2,267, 대기 69)이고 오류, 사전밖, 매핑없음은 없다.

화면이 지킬 것

- 요약의 수를 그대로 쓰고, 엣지를 따라 다시 세지 않는다(보유 담보 수, 보장 대분류별 수, 담보를 가진 종형, 미연결 급부 수). 요약과 엣지가 맞는지는 `tests/test_graph_data.py`가 본다.
- 비교 대상 종형은 `맞붙는종형`을 쓰고 화면에서 선택하지 않는다. 시안 4 안에서는 sales.json의 `기준별[].맞붙는종형`과 같은 값이다.
- 담보 수를 보일 때 `미연결사유`의 대기가 0보다 크면 그 종형의 담보가 더 있을 수 있다는 것을 함께 적는다(검수 대기). 대상외(매핑 대상 외)는 표준담보가 아닌 급부라 빠진 담보로 적지 않는다.
- 비교역할이 `관문전용`(화면 이름 인수기준만 수집. 급부가 없으면 `표준담보`가 빈 목록)과 `직전개정시연`(화면 이름 직전 개정 상품)인 종형은 담보 비교의 대상이 아니다. `비교역할`과 `판매종료일`로 구분하고, 담보가 없다고 적지 않는다.
- 비교역할, 미연결사유, 속성 이름을 화면에 낼 때는 `표시명`을 거친다(아래 절). 노드 종류와 엣지 종류의 이름은 `kinds`, `ekinds`를 그대로 쓴다.

## 시안 4의 열쇠와 같은가

- 종형ID: 같은 글자다. sales.json의 `종형` 열쇠, `기준종형[].종형ID`, `기준별` 열쇠와 `맞붙는종형` 값, cover.json의 `b` 열쇠와 `cols`는 모두 graph.json의 종형 노드 ID(`summary.종형`의 열쇠)다. 이어 주는 표는 싣지 않는다.
- 표준담보ID: 같은 글자다. cover.json `rows`의 첫 칸은 표준담보 노드 ID다. 다만 graph.json은 사용여부가 참인 표준담보만 노드로 싣고 sales.json의 `표준담보`는 사용여부가 거짓인 담보(지금 `STD_HT_DX_CARDIO`)도 싣는다. 그 담보는 graph.json에 노드가 없다.
- 종형의 범위: graph.json은 화면에 올린 회사의 종형 23개를, sales.json의 `종형`은 19개를 싣는다. graph.json에만 있는 넷은 우체국 직전개정시연 종형 셋과 한화생명 관문전용 간편가입형(10년)이다.
- 위 셋은 자료 시각이 같을 때 `tests/test_graph_data.py`가 확인한다.

## 화면이 자료를 읽는 자리 (graph2.html)

- `tpl.html`의 `<script type="application/json" id="gdata">__DATA__</script>`에 `build.py`가 graph.json을 넣는다(`</`는 `<\/`로 바꿔 넣는다).
- 스크립트 첫머리에서 `RAW=JSON.parse(#gdata)`로 읽고, `KIND=RAW.kinds`, `EK=RAW.ekinds`, `KEYS=RAW.keys`로 받은 뒤 `N`(노드), `E`(엣지)로 풀어 쓴다. 속성은 `dec()`가 `keys`로 이름을 되돌린다. 탐색 시안은 `summary`를 읽지 않는다.
- 회사 색과 배지는 `MAIN=['EPOST','HANWHALIFE','SAMSUNGFIRE']`와 CSS 변수 `--o-<기관코드>`로 정하고, 나머지 회사는 `--o-OTHER`로 그린다.
- 시작 버튼은 `MAIN`의 회사 셋과 `STARTS`(표준담보 이름 목록)다. 시작 카드 머리의 노드 수는 `N.length`다(2026-11-23 전에는 3,744를 글자로 박아 두었다).
- 글꼴은 `<style>/*__FONTS__*/</style>` 자리에 `proto_src/fonts/fonts_graph2.css`가 들어간다(PLDisplay, PLBody, PLNum, PLWide).
- 2026-11-23 사본(노드 9,509, 엣지 13,802)에서 380px, 1280px 폭으로 열어 시작 버튼 여덟을 눌러 이웃을 펼치고, 한화생명 일반가입형에서 같은 회사의 다른 종형으로 넘어가 보았다. 콘솔 오류와 외부 요청은 없었다.

## 화면 용어와 표시명 (2026-11-24 추가)

시안 4의 규약(`proto_src/console4/API.md` 맨 끝 "화면 용어와 표시명")과 같은 방식이다. 화면 코드가 키로 쓰는 시트 값과 속성 이름은 바꾸지 않고, 화면에 보일 이름을 `표시명`(평면 맵 `{키 값: 화면 이름}`)으로 싣는다.

| 구분 | 키 → 화면 이름 | 키로 쓰는 곳 |
| --- | --- | --- |
| 비교역할 | 관문전용 → 인수기준만 수집, 직전개정시연 → 직전 개정 상품 | `summary.종형[].비교역할`(시트 허용값) |
| 미연결사유 | 대상외 → 매핑 대상 외 | `summary.종형[].미연결사유`의 열쇠(`hum_담보매핑` 검토상태 값). 대기, 오류, 사전밖, 매핑없음은 대조표에 행이 없어 싣지 않았다 |
| 속성 이름 | 검토상태 → 검수 상태 | `keys`의 속성 이름(매핑 엣지의 속성) |

노드 종류와 엣지 종류는 표시명에 싣지 않고 `kinds`, `ekinds`의 이름 자체를 화면 이름으로 바꿨다: 보장분야 → 보장 대분류, 소식 → 시장 동향, 해당 → 매핑, 속함 → 분류, 관계 → 담보 관계, 일으킴 → 발표. 짧은 표기(열 이름 자리의 동향, 관계, 대분류)는 자료에 싣지 않고 화면 문구 표에서 정한다. 화면 코드에 예전 이름을 기본값으로 적어 둔 목록(시안 4 `tab6.js`의 `kinds`, `ekinds` 기본 목록, 이 화면 `tpl.html`의 `eShort`)은 자료의 이름과 같게 맞춘다.

```js
const glabel = v => (RAW['표시명'] && RAW['표시명'][v]) || v;
glabel(vs['비교역할']);   // '관문전용' → '인수기준만 수집'
glabel('대상외');         // '매핑 대상 외'
glabel('검토상태');       // 속성 이름 표시 '검수 상태'
RAW.kinds[5];             // '보장 대분류'
RAW.ekinds[2];            // '매핑'
```

규약 테스트: `tests/test_display_names.py`(표시명과 종류 이름), `tests/test_graph_data.py`.
