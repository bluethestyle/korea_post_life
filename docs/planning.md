# 우체국보험 상품·청약 판단 지원 앱 기획 확정본

기준일: 2026-11-19

개정: 2026-11-18에 공시 문서를 실제로 받아 확인한 내용을 반영했습니다. 비교 대상 명칭을 고쳤고, 보험료 비교를 2단계로 옮겼으며, 화면 4를 다시 정의하고, 고지 범위 열 두 개를 더했습니다(12.4). 2026-11-19에 정밀 비교 대상을 생명보험 10곳과 손해보험 9곳으로 넓히고, 기존 상품의 초기 적재와 신상품, 개정 상품 운영의 추출 방식을 나누었으며, 표준담보 사전을 넓히고 급부에 지급기준구분 열을 더하기로 한 결정을 적었습니다(열은 5.5의 표에 아직 넣지 않았습니다).

## 1. 개요

우체국보험 본부의 상품·영업지원 담당자가 조건을 고르면, 타사 대비 우위·열위와 빈자리를 화면에서 바로 판단할 수 있게 돕는 앱입니다.

| 항목 | 확정 내용 |
| --- | --- |
| 주 사용자 | 본부 상품·영업지원 담당자. 창구 직원과 FC에게는 1장짜리 응대 카드로 전달 |
| 관점 | 우체국보험의 청약(가입 적격)과 상품 영업 |
| 자료 | 공개 자료만 사용 (상품요약서, 사업방법서, 약관 별표, 보도자료, 뉴스, 협회 게시판) |
| 형태 | 시각화 중심의 판단 지원 화면. 화면마다 충분한 해설 글을 붙이고, 질문 응답은 보조 기능 |
| 제출처 | AI 도구·에이전트 활용 공모전 |
| 제약 | 개념검증 단계, 정기 주간 운영은 무료 API 한도 안에서(기존 상품의 초기 적재에는 코드 규칙과 구독 도구를 씀), 1인 구축 |

**핵심 메시지**: 최신 판정 전용 AI를 작업별 분업 구조에 넣고, 검증 장치와 함께 적용했다.

**전체 흐름**

1. 수집: 공시 문서와 시장 소식을 모읍니다.
2. 추출: 기존 상품의 초기 적재는 코드 규칙이나 구독 도구(Claude 서브에이전트, 제미나이 구독 패널)로 구조화하고, 신상품과 개정 상품은 API 생성 모델이 표와 문장에서 값을 뽑습니다.
3. 검증·분기: 코드와 판정 모델이 값을 대조하고, 확신이 낮은 건은 사람 검토로 넘깁니다.
4. 지식그래프: 검증을 거친 값과 관계만 쌓습니다.
5. 판단 화면: 조건을 고르면 비교 결과와 근거가 나옵니다.

## 2. 범위

범위는 두 층으로 나눕니다. 상품을 깊게 비교하는 정밀 비교 층은 우체국보험과 생명보험 10곳, 손해보험 9곳(재보험 전업 제외)의 일반심사 종합 건강보험과 간편심사 건강보험으로 넓히고, 대형사부터 한 회사씩 적재합니다. 시장 소식을 모으는 동향 층은 19개 기관 전체를 다룹니다.

### 2.1 정밀 비교 대상

정밀 비교 대상 회사는 생명보험 10곳과 손해보험 9곳입니다. 수입보험료 순위표를 찾지 못해 총자산 기준으로 골랐고 출처가 기사여서, 순위는 공식 통계로 확정하지 못했습니다. 재보험 전업인 코리안리는 뺐습니다. 회사마다 우체국 상품과 견줄 일반심사 종합 건강보험과 간편심사 건강보험 두 종류만 넣고, 대표 상품은 각 회사 공시실의 판매 목록에서 확인해 정합니다. 적재는 한 회사씩 합니다. 급부가 표로 적혀 있어 기계 대조를 하기 좋은 손해보험사를 먼저 넣고, 생명보험사를 다음에 넣으며, 같은 업권 안에서는 대형사부터 넣습니다.

- 회사별 대표 상품 후보는 공시실 판매 목록을 조사해 추렸고, 상품명과 급부 절의 꼴은 docs/progress.md의 "비교 대상 확대: 회사별 상품공시 접속 모듈 (2026-11-19)" 절 표에 있습니다. 조사한 에이전트가 고른 후보일 뿐 확정한 것이 아닙니다. 주력 상품이 둘 이상이라 확신이 낮다고 적은 회사도 있습니다(DB손해보험 일반심사, 삼성생명 간편심사 등). DB손해보험은 접속 모듈을 시범으로 먼저 만든 회사라 그 표에 줄이 없습니다.
- 신한라이프는 한 상품 안에 일반심사형과 간편심사형이 함께 있어 두 칸이 같은 상품입니다.
- 한화손해보험은 접속 모듈을 만들지 못했습니다. 공시 화면은 GitHub Actions에서 열리지만(이 PC의 망에서는 TLS 연결 단계에서 거부됨), 상품 목록 요청이 자동 접속 차단에 걸려 상태 400이 돌아옵니다. 차단을 우회하지 않기로 했으므로, 이 회사 문서는 사람이 공시실에서 내려받아 넣어야 합니다.
- 미래에셋생명은 요약서와 사업방법서 네 문서(476쪽) 모두 본문 글자가 그림으로 들어 있어 글자가 풀리지 않습니다. 쪽을 그림으로 만들어 제미나이 구독 패널에 넘겨 글자로 옮기는 방법을 2026-11-19에 시험했고(글자를 풀 수 있는 다른 문서의 한 쪽에서 실제 글자 1,123자와 모두 일치), 이 방법으로 옮긴 글을 원문 글자로 삼아 적재합니다.
- 건강고지 할인형과 납입면제형은 비교에서 뺍니다. 우량체 할인 보험료가 섞이면 우체국 일반심사 보험료가 비싸 보입니다.
- 환급 유형은 우체국 종형과 같은 것을 고릅니다. 같은 유형이 없으면 가장 가까운 종을 쓰되 화면에 "구조 상이"로 표시합니다.
- 한화생명의 나머지 간편가입형((0년)·(3년)·(4년)·(10년))과 건강가입형은 화면 2의 관문 유무 표시에만 씁니다. 공시 서류는 "3·1·5"가 아니라 "간편가입형(1년)"으로 적습니다. 알릴의무 질문 구조로 보면 (1년)이 3·1·5, (2년)이 3·2·5, (5년)이 3·5·5에 해당합니다.
- 우체국하나로OK보험 2609는 주계약이 종신·정기 기반이라 2차 확장으로 미룹니다.
- 우체국보험, 한화생명, 삼성화재의 상품 코드와 종 구성은 2026-11-18에 각 사 공시실에서 확인했습니다(12.4).
- 한화생명 "시그니처 H통합건강보험"은 2026-05-03에 판매를 마치고 "시그니처 H통합보험"으로 이어졌습니다. 삼성화재 "마이헬스 파트너"는 2026-10-11에 판매를 마쳤고, 같은 상품코드 계열이 "THE FIT 파트너"로 이어집니다.
- 한화생명과 삼성화재 새로고침 7·8종은 해약환급금 미지급형만 판매합니다. 우체국 상품과 환급 구조가 달라 "구조 상이" 표시 대상입니다.
- 삼성화재 새로고침 8종(일반고지)은 우체국간편한건강보험 4종(일반가입)의 짝으로 비교 대상에 넣습니다. 표 추출기가 8종 요약서에서 이름을 깨뜨리는 다섯 곳을 고치고, 7종처럼 독립 구조화와 대조를 거친 뒤 적재합니다.

### 2.2 시장 동향 수집 대상

자동차·변액·재보험 전업사를 뺀 19개 기관입니다. 정밀 비교 대상(2.1)과는 회사 구성이 달라, 라이나생명과 KDB생명은 동향 수집에만 있고 KB라이프생명, 미래에셋생명, 메트라이프생명은 정밀 비교에만 있습니다.

- 생명보험 9곳: 삼성생명, 한화생명, 교보생명, 신한라이프, NH농협생명, 라이나생명, 동양생명, 흥국생명, KDB생명
- 손해보험 9곳: 삼성화재, DB손해보험, 현대해상, KB손해보험, 메리츠화재, 한화손해보험, NH농협손해보험, 롯데손해보험, 흥국화재
- 우체국보험

모으는 소식은 일곱 가지입니다: 배타적 사용권, 신담보 출시, 상품 개정, 판매중지, 간편고지 완화, 가입 한도의 한시 상향, 제도 변화. 자동차보험, 퇴직연금, 변액보험, 인사, 실적, 사회공헌, 경품 행사 소식은 버립니다.

| 6 | AI 작업 내역 | 추출·판정·반려·재추출 기록, 판정 확률 | 전체 작업 |

### 3.1 화면 규칙

- 문장을 입력하는 대신 조건(상품군, 나이대, 성별, 심사 유형, 갱신 유형, 환급 유형)을 고릅니다.
- 모든 화면에 비교 기준(우체국 상품 대 민영 비교사)을 둡니다.
- 칸을 누르면 근거 경로와 출처가 열립니다. 공시 문서는 파일 주소가 고정돼 있지 않아, 공시 목록 화면 주소와 문서 종류·개정 연월을 함께 보여 줍니다. 쪽수는 급부 값에만 붙이고, 그 밖의 값은 문서 종류나 별표명까지 보여 줍니다.
- 병력으로 인수 가부를 단정하지 않습니다. 화면 2는 나이·기간·한도 적격과 간편심사 고지 관문까지만 다룹니다.

### 3.2 색상 기준

- 1단계의 우열 표시는 문서에 적힌 보장 조건으로 켭니다: 감액 기간과 지급률, 면책기간, 지급 개시 조건(예: 입원 1일째부터인지 4일째부터인지), 지급 한도 일수, 가입 최고나이.
- 가격 색은 보험료 자료가 들어오는 2단계에 켭니다. 심사 유형, 갱신 유형, 환급 유형이 모두 같은 상품끼리만 켭니다.
- 가격 기준은 민영 비교사 평균 대비 우체국 격차율입니다. ±10%를 넘으면 우위·열위로 표시하고, 이 값은 기준값 탭에서 조정합니다. 비교사가 생명보험 10곳과 손해보험 9곳으로 늘었으므로, 전체 평균을 쓸지 업권별(생명보험, 손해보험) 평균을 쓸지는 보험료 자료가 들어오는 2단계에 정합니다.
- 구조가 다른 행은 가격 색을 끄고 "구조 상이" 표시만 붙입니다.
- 면책·감액이 불리한 경우는 가격 색과 분리한 별도 표식으로 알립니다.

### 3.3 보험료 비교와 특약 조합 규칙

- 공시 서류(상품요약서, 사업방법서)에는 특약 단위 보험료가 없습니다(12.4). 보험료 비교는 2단계에 각 사 공시실의 보험가격공시실에서 주력 담보 8\~10개와 대표 연령 1\~2개만 받아서 합니다. 출처구분은 "계산기"입니다.
- 요약서에 실린 가입 예시의 보험료는 화면에 내지 않습니다. 회사마다 묶인 특약과 연령이 달라, 나란히 놓으면 오해를 부릅니다.
- 총 가입 한도가 아니라 급부별 비교 단위당 보험료로 비교합니다. 단위는 진단 1,000만 원, 수술 100만 원, 입원일당 1만 원입니다.
- 보험료 기준은 50세 남녀를 우선으로 합니다. 비갱신형은 20년납, 갱신형은 전기납입니다.
- 주급부와 부수급부로 이뤄진 특약(예: 일반암 진단 + 소액암 진단)은 주급부 기준으로 환산하고, 부수급부는 환산 대상에서 뺍니다.
- 주급부를 하나로 정할 수 없는 대등 결합 특약(예: 암입원 + 암수술)은 특약 단위 보험료를 그대로 싣고 "복합" 표시를 붙입니다. 격차율 계산에서는 뺍니다.
- 화면 4의 특약 조합은 고른 특약의 가입금액에서 담보별 실제 지급액을 계산해 보여 줍니다. 가입금액과 지급액이 다른 특약이 많기 때문입니다(예: 우체국통합건강보험 2504의 암보장특약은 가입금액 2,000만 원에 일반암 3,000만 원을 지급).
- 조합은 화면에서 바로 계산합니다. 추천 목적 세 가지(암 집중, 3대 질병 균형, 입원·수술 실속)를 출발점으로 제공하고, 나이별 한도 축소와 선행·연동 제약에 걸리는 조합은 내지 않습니다.
- 보험료 합계("선택특약 합계"와 "주계약 포함 실납입액")는 2단계에 붙입니다.

### 3.4 해설 글과 질문 응답

- 화면마다 결론 한 줄, 읽는 법, 이유 설명, 실무 유의점, 출처를 붙입니다.
- 해설은 화면 × 상품군 단위로 주 1회 미리 만듭니다. 비교 판정이 있는 화면 3은 우위·대등·열위 세 벌을 준비하고, 화면은 고른 조건에서의 보장 조건 비교 결과에 맞는 문장을 보여 줍니다. 2단계부터는 평균 격차율도 함께 봅니다. 고르는 기준은 기준값 탭에 둡니다. 조건에 따라 결론이 뒤바뀌는데 문장은 그대로인 일을 막기 위함입니다.
- 글 속 숫자는 모델이 쓰지 않습니다. 모델은 변수 자리만 남기고, 화면이 데이터 값을 끼워 넣습니다. 변수 밖의 숫자가 섞인 글은 폐기하고 다시 만듭니다.
- 질문 응답은 미리 만든 답변과 화면 안 검색으로 제공합니다. 실시간 질문 기능은 1차에서 뺍니다.

### 3.5 응대 카드

- A4 1장 PDF로 출력합니다. 화면에서 고른 기준 종형과 비교 종형 한 쌍을 한 장에 담습니다.
- 상단에 "내부 교육·비교 참고용(대외 배포 금지)" 표식을 고정합니다. 타사 실명과 보험료 우열이 적힌 자료를 고객에게 그대로 건네지 않게 하기 위함입니다.

## 4. 자료와 수집

자료는 바뀌는 주기가 달라 두 갈래로 나눠 다룹니다. 공시 문서는 기존 상품을 한 번 초기 적재한 뒤 상품이 개정될 때만 다시 추출하고, 시장 소식은 매일 조금씩 모아 일요일에 마감합니다.

| 층 | 자료 | 주기 | 실행 위치 |
| --- | --- | --- | --- |
| 기준 자료 | 상품요약서, 사업방법서, 약관 별표 | 상품 개정 시 (기존 상품은 초기 적재 1회) | GitHub Actions(수집, 신상품과 개정 상품의 API 추출), 초기 적재는 코드 규칙과 구독 도구 |
| 시장 동향 | 뉴스, 보도자료, 협회 게시판 | 매일 소량, 주 1회 마감 | GitHub Actions |
| 협회 통계 | 생보·손보협회 통계 | 2차 확장 | 미정 |

### 4.1 공시 문서 추출

기존 상품의 초기 적재와 신상품, 개정 상품의 운영은 추출 경로를 나눕니다. 무료 API 한도는 신상품과 개정 상품의 추출, 그리고 판정에만 씁니다.

| 구분 | 대상 | 추출 방식 | 검증 방식 | API 무료 한도 쓰임 |
| --- | --- | --- | --- | --- |
| 초기 적재 | 지금 판매 중인 비교 대상 상품 | 표가 규칙적인 문서는 코드 규칙, 그 밖의 문서는 Claude 서브에이전트나 제미나이 구독 패널로 구조화 | 코드 대조, 판정 전용 모델, 정답셋, 교차 확인 | 판정 모델만 씀 (추출 모델은 쓰지 않음) |
| 이후 운영 | 신상품, 파일 해시가 바뀐 개정 상품 | API 생성 모델(3.5 Flash Lite, 보조 3.1 Flash Lite) | 코드 대조, 판정 전용 모델, 반려 시 재추출 | 신상품과 개정 상품의 추출과 판정 |

- 상품요약서와 사업방법서를 주 원천으로 삼습니다. 가입나이, 한도, 예시 보험료, 면책·감액 조건이 여기에 모여 있습니다.
- 약관은 통째로 모델에 넣지 않습니다. 목차와 별표(질병·수술 분류표) 구간만 잘라 넣습니다.
- 파일 해시가 바뀐 상품만 다시 추출합니다.
- 원본 PDF는 저장소에 올리지 않고 출처 링크와 추출 결과만 남깁니다.
- 우체국보험은 협회 비교공시 대상이 아니라 자체 공시실에서 따로 받고, 민영사와 같은 스키마로 합칩니다.

### 4.2 시장 동향 수집 경로

- 주 경로: 검색 그라운딩. 1차 호출에서 검색 결과를 산문으로 받고, 2차 호출에서 정형화합니다.
- 예비 경로 ①: 생보·손보협회의 배타적 사용권 게시판을 주 1회 읽습니다.
- 예비 경로 ②: Google News RSS에서 제목, 매체명, 발행일, 링크만 읽습니다. 기사 본문은 수집하거나 저장하지 않습니다.
- 예비 경로 ③: 우체국보험과 정밀 비교 대상 가운데 먼저 넣는 회사의 공식 뉴스룸만 직접 확인합니다.
- 네이버 검색 API는 쓰지 않습니다. 개정 약관이 검색 결과를 AI 답변 생성에 쓰는 것과 21일을 넘는 서버 보관을 제한합니다.

### 4.3 기간 조건을 지키는 방법

검색 모델이 "최근 한 달" 같은 조건을 놓치는 것이 시험에서 확인됐습니다(12장). 세 단계로 막습니다.

1. 질의에 상대 시점 표현을 쓰지 않고, 배치가 계산한 날짜를 적어 넣습니다.
2. 소식마다 발행일을 먼저 적게 하고, 발행일이 불분명한 건은 빼게 합니다.
3. 정형화 직후 코드가 발표일자를 확인해, 수집 구간 밖의 행을 버립니다.

### 4.4 요일별 수집 분할

하루 5\~6회만 호출해 하루 20회 한도 안에 재시도 여유를 남깁니다. 2\~3개사를 한 묶음으로 질의합니다.

| 요일 | 대상 | 호출 수 |
| --- | --- | --- |
| 월 | 생보 대형 3사 (삼성·한화·교보) | 6 |
| 화 | 손보 대형 3사 (삼성화재·DB·KB) | 6 |
| 수 | 손보 주력 3사 (현대해상·메리츠·한화손보) | 6 |
| 목 | 생보 중견·특화 6사 | 6 |
| 금 | 손보 중견 3사 + 우체국보험 | 5 |
| 토 | 협회·당국 공통 (배타적 사용권, 제도 변화) | 5 |
| 일 | 실패 건 재수집, 주간 마감과 해설 생성 | 예비 |

### 4.5 접속 시험

국내 공시실과 협회 사이트가 GitHub Actions의 해외 주소를 막는지는 첫 주에 실제로 접속해 확인합니다. 막히면 그 수집만 로컬에서 실행해 결과를 시트에 씁니다.

### 4.6 중복 소식 병합

검색 그라운딩이 돌려주는 주소는 호출마다 달라지고 RSS 주소도 매체마다 달라, 주소만으로는 같은 기사를 걸러 내지 못합니다.

- 출처 주소는 가능한 한 실제 기사 주소로 풀어서 저장합니다.
- 시트에 쓰기 전에 같은 기관·분류유형·수집주차 안에서 제목과 요약이 비슷한 소식을 하나로 합칩니다.
- 애매한 쌍은 판정 모델에 "같은 사건인가"를 물어 가립니다.

## 5. 지식DB 구조

정본은 구글 시트 한 파일(postlife\_graph\_data)이고, 탭 13개로 나눕니다. Apps Script는 쓰지 않고, 배치와 로컬 스크립트가 서비스 계정으로 읽고 씁니다.

### 5.2 그래프 구성 원칙

- 여러 대상이 공유하거나 관계를 따라 건너가야 하는 것은 노드입니다: 기관, 모상품, 개정판, 종형, 특약, 급부, 표준담보, 표준질병군, 법정 한도, 시장 소식.
- 한 대상에만 붙는 값은 속성입니다: 보장금액, 면책일수, 감액률, 가입나이, 보험료.
- 노드 사슬은 종형 → 특약 → 급부 → 표준담보입니다. 특약은 결합 제약과 보험료의 단위이고, 급부는 표준담보에 연결되는 단위입니다.
- 급부는 표준질병군과도 직접 이어집니다. 같은 표준담보라도 상품마다 보장하는 질병 범위가 달라, 이 연결이 있어야 보장 폭을 비교할 수 있습니다.
- 급부 → 표준질병군 연결은 시트에 적지 않습니다. 배치가 sys\_급부질병코드의 포함·제외 구간과 hum\_표준질병군의 코드 범위를 대조해 만듭니다.
- 시트에 노드·엣지 탭을 따로 두지 않습니다. 탭의 행이 노드이고, 다른 탭을 가리키는 ID 열이 엣지입니다. 배치가 탭을 읽어 그래프로 조립합니다.
- 그래프는 네 곳에만 씁니다: 칸을 눌렀을 때의 근거 경로, 담보 구성이 비슷한 타사 상품 찾기, 특약 결합 제약 탐색, 개정 파급 추적. 나머지 화면은 표 조회로 처리합니다.

### 5.3 ID 규칙

- 일련번호를 쓰지 않습니다. 문서를 다시 추출해도 같은 ID가 나오도록 기관코드 + 공시상품코드 + 정규화한 이름의 해시로 만듭니다. 사람이 검토한 행과의 연결이 끊기지 않게 하기 위함입니다.
- 개정판ID는 모상품ID + 개정 연월로 만듭니다(예: EPOST\_SIMPLE\_2606). 한 개정판 안의 종마다 공시상품코드가 다를 수 있어, 공시상품코드는 종형 단위에만 둡니다.
- 종형계보키(모상품ID + 심사유형 + 간편고지약칭 + 갱신유형 + 환급유형)로 개정 전후의 같은 종형을 잇습니다.
- 특약명에는 개정 연월(2504 등)이 붙어 있습니다. 연월을 떼 이름으로 만든 특약계보키를 함께 두고, 같은 종형 계보 안에서만 개정 전후 특약을 잇습니다.

### 5.4 쓰기 규칙

- 쓸 때는 입력값을 그대로 넣는 옵션(RAW), 읽을 때는 서식 없는 값 옵션을 씁니다. 앞자리 0이 잘리거나 3.2.5가 날짜로 바뀌는 것을 막습니다.
- 행 단위로 호출하지 않고 탭 단위로 한꺼번에 읽고 씁니다.
- 상품 하나만 다시 추출할 때 탭을 통째로 비우지 않습니다. 탭 전체를 읽어 종형ID → 특약ID → 급부ID 사슬로 그 종형의 기존 행만 걷어내고, 새 행을 합쳐 다시 씁니다.
- 누적 탭(sys\_시장동향, sys\_작업로그)은 다시 쓰지 않고 끝에 행을 덧붙입니다.
- 시트 안에 조회 수식을 두지 않습니다. 계산으로 나오는 값(기준 단위당 보험료, 복합특약 여부 등)도 저장하지 않고 배치에서 계산합니다.
- 한 셀에 여러 값을 넣지 않습니다. 예외는 sys\_시장동향의 관련표준담보ID 한 열뿐이고, 세미콜론으로 구분합니다.
- sys\_ 탭은 보호를 걸어 서비스 계정만 고치게 합니다.
- 담보 매핑의 정본은 hum\_담보매핑 한 곳입니다. 배치는 새 급부의 행을 추가하고 확률이 높은 건을 자동 확정하거나 대상외로 분류할 뿐, 담당자가 손댄 행(검토상태가 승인·수정·오류)은 읽기만 합니다. 급부ID가 재추출해도 바뀌지 않으므로, 문서를 다시 추출해도 매핑이 유지됩니다.

## 6. 모델 분업과 검증

글을 쓰는 일은 생성 모델에, 맞는지 가리는 일은 판정 전용 모델과 코드에 맡깁니다. 판정 전용 모델은 글을 쓰지 않고, 정해진 선택지에 확률만 매기는 모델입니다.

### 6.1 작업별 배정

한도는 2026-11-18에 AI Studio 한도 화면에서 읽은 무료 티어 값입니다.

| 작업 | 모델 | 하루 한도 | 분당 한도 |
| --- | --- | --- | --- |
| 시장 소식 검색 수집 | gemini-2.5-flash-lite + 검색 그라운딩 | 20회 | 10회, 25만 토큰 |
| 신상품과 개정 상품 추출, 분류, 해설 작성 | gemini-3.5-flash-lite (보조: 3.1 Flash Lite) | 각 500회 | 15회, 25만 토큰 |
| 기존 상품 초기 적재 추출 | 코드 규칙(표가 규칙적인 문서), Claude 서브에이전트, 제미나이 구독 패널 | API 추출 한도를 쓰지 않음 | 검증은 코드 대조, 판정 모델, 정답셋, 교차 확인으로 함 |
| 담보 매핑 분기, 기사 선별, 추출값 정합성 채점 | gemini-decision-1 | 10,000회 | 200회, 5만 토큰 |
| 반려 건 재추출 | 3.1 Flash Lite 또는 Gemma 4 | Gemma 4는 14,400회 | Gemma 4는 30회, 1.6만 토큰 |
| 주간 요약 최종본 | gemini-3.8-flash | 20회 | 5회, 25만 토큰 |
| 조항 검색용 임베딩 (2차) | Embedding 2 | 1,000회 | 100회, 3만 토큰 |
| 숫자 대조, 날짜 검증, 주간 변화 집계 | 코드 | 한도 없음 |  |

- 검색 그라운딩은 2.5 계열에서만 무료로 열려 있습니다(하루 1,500회). 3 이상 계열은 0회입니다.
- gemini-2.5-flash는 2026-12-01부터 요청이 gemini-3.5-flash-lite로 자동 전환됩니다. 그래서 검색 수집은 처음부터 2.5 Flash Lite로 잡습니다.
- 2.5 Flash Lite도 구형 계열이라 언젠가 닫힐 수 있습니다. 4.2의 예비 경로를 함께 만들어 둡니다.
- Gemma 4는 분당 토큰이 적어 대량 추출에 쓰지 않습니다. 쓸 때는 표 조각을 1,200\~1,500토큰 이내로 자릅니다.

### 6.2 검증 흐름

1. 추출: 기존 상품의 초기 적재는 코드 규칙이나 구독 도구(Claude 서브에이전트, 제미나이 구독 패널)가, 신상품과 개정 상품은 3.5 Flash Lite가 표 조각에서 값을 뽑습니다.
2. 코드 대조: 글자 그대로 비교되는 숫자와 논리 규칙(최저나이가 최고나이보다 크지 않은가 등)을 코드가 먼저 확인합니다.
3. 판정: 표현이 달라 해석이 필요한 항목만 판정 모델에 넘겨 원문과 일치하는지 확률로 받습니다.
4. 분기: 확률에 따라 자동 확정, 사람 검토, 재추출 세 구간으로 나눕니다.
5. 재추출: 반려된 항목은 추출과 다른 모델로 다시 뽑습니다.
6. 기록: 모든 단계를 sys\_작업로그에 남기고 화면 6에 공개합니다.

담보 매핑도 같은 방식입니다. 판정 모델이 표준담보 사전에서 하나를 고르면 결과가 hum\_담보매핑에 급부마다 한 행씩 쌓입니다. 확률이 낮은 건은 검토 대기로 남아 담당자가 확정합니다. 화면 데이터는 매주 이 탭을 읽어 조립하므로, 담당자가 고친 내용이 다음 주 화면에 바로 반영됩니다.

### 6.3 판정 모델 사용 규칙

- 구간 경계값은 정답셋으로 맞춥니다. 임의의 기준선(예: 0.85)을 그대로 쓰지 않습니다.
- 해석 규칙을 문항에 적습니다. 예: "'90일이 지난 날의 다음날'은 면책기간 90일로 본다."
- 선택형 문항에는 "해당 없음"을 반드시 둡니다.
- 표준담보가 255개를 넘으면 대분류를 먼저 고르고 세부를 고르는 두 단계로 나눕니다.
- 판정 모델이 막히면 코드 대조와 3.1 Flash Lite 검증으로 돌아갑니다.

## 7. 배포 구조

서버와 별도 DB를 두지 않습니다. 배치가 결과를 미리 계산해 파일로 저장하고, 정적 화면이 그 파일을 읽어 보여 줍니다.

| 구성 요소 | 위치 | 역할 |
| --- | --- | --- |
| 정본 데이터와 담당자 검토 | 구글 시트 (postlife\_graph\_data) | 탭 13개. 서비스 계정으로 읽고 씀 |
| 코드, 기획 문서, 화면 파일, 주간 데이터 사본 | GitHub 저장소 bluethestyle/korea\_post\_life (공개) | 사본이 커밋으로 쌓여 개정 이력이 됨 |
| 시장 소식 수집, 주간 마감, 해설 생성, 그래프 계산 | GitHub Actions 예약 실행 | 매일 소량 수집, 일요일 심야 마감 |
| 판단 화면 | GitHub Pages | 저장소의 데이터 파일을 읽는 정적 화면 |
| 공시 문서 수집과 추출 | GitHub Actions (초기 적재는 로컬 PC) | 수집과 신상품, 개정 상품 추출은 Actions에서 API 모델로 실행. 기존 상품의 초기 적재는 코드 규칙과 구독 도구로 구조화하고 검증을 거쳐 시트에 씀 |

- 무료 계정의 Pages는 공개 저장소에서만 열립니다. 공개 자료만 쓰는 앱이라 공개 상태를 유지합니다.
- 화면은 시트를 직접 읽지 않습니다. 배치가 시트 내용을 파일로 떠서 저장소에 올리고, 화면은 그 파일만 읽습니다.
- 그래프 탐색과 유사도 같은 무거운 계산은 배치에서 끝냅니다. 한도 보완 조합만은 경우의 수가 많아 미리 계산하지 않고, 화면이 제약과 보험료 데이터를 읽어 바로 계산합니다.

### 7.1 비밀값과 시트 설정

- Gemini API 키와 구글 서비스 계정 키는 Actions 비밀값에만 넣습니다. 저장소 파일에는 절대 적지 않습니다.
- 시트 공유는 "제한됨"으로 두고, 서비스 계정 이메일만 편집자로 추가합니다.
- 시트 시간대는 서울로 맞춥니다. 지금은 GMT라 수집 시각과 주차 구분이 어긋납니다.
- API 키는 기존 앱과 다른 새 프로젝트에서 발급해 한도를 따로 씁니다.

## 8. 개정 이력과 주간 변화

보험사의 실제 개정과 우리 데이터의 정정을 코드에서 갈라 다룹니다. 갈라 놓지 않으면 담당자의 오타 수정이 타사 약관 개정으로 잘못 알려집니다.

| 구분 | 판별 기준 | 보내는 곳 |
| --- | --- | --- |
| 개정 | 같은 모상품 아래 새 개정판ID가 생기고 직전 판의 판매종료일이 닫힘 | 화면 1, 화면 5 |
| 정정 | 같은 개정판ID 안에서 지난주 사본과 값이 달라짐 | 화면 6 |

- 주간 사본은 기본키 오름차순, 열 이름 순서 고정의 JSON Lines 파일로 저장합니다. 행 순서나 실행 시각 때문에 거짓 변경이 잡히지 않게 하기 위함이고, 실행 시각은 별도 파일에 둡니다.
- 개정 전후 비교는 특약계보키로 같은 특약을 이어서 합니다.
- 화면 1의 "이번 주 달라진 점"은 세 가지만 코드가 먼저 추려 확정합니다: 이번 주에 등록·판매종료된 개정판, 이번 주차의 시장 소식, 대표 조건에서 우열 표시가 바뀐 표준담보(1단계는 보장 조건, 2단계부터 가격 포함). 대표 조건(예: 50세 남녀, 일반심사와 간편 325)은 기준값 탭에 지정합니다.
- 3.8 Flash는 확정된 목록만 읽고 요약 문장을 씁니다.

| 3단계 | 판단 ⑩ 개정 파급 추적, 2차 확장 상품 | 화면 5에 개정 파급 추가 |

- 표준담보 매핑이 먼저인 이유: 회사마다 특약명이 달라, 매핑 없이는 면책·감액이나 보험료를 같은 행에 놓을 수 없습니다.
- 특약 조합(⑧)과 결합 제약(③)을 함께 만드는 이유: 제약을 빼고 조합하면 실제로 청약할 수 없는 특약 조합이 나옵니다.
- 보험료(⑥)를 2단계로 옮긴 이유: 공시 서류에 특약 단위 보험료가 없어, 보험가격공시실에서 따로 받아야 합니다.
- 직전 개정판 1종은 1단계에서 함께 넣어, 개정 전후 비교를 처음부터 보여 줍니다.
- 검증 단계의 반려·재추출 기록은 구축 중에도 지우지 않고 쌓습니다. 공모전 증거로 씁니다.
- 화면 1, 화면별 해설 글, 응대 카드, GitHub Pages 배포 워크플로, 삼성화재 공시 문서 수집 연결은 2026-11-19에 이미 만들었습니다. 응대 카드는 2단계에 두었던 것을 보험료 없이 보장 조건 비교만으로 먼저 만든 것입니다. 경과는 docs/progress.md에 있습니다.
- 손해보험사를 먼저 넣는 이유: 손해보험사 요약서는 급부가 쪽을 넘어 이어지는 표로 적혀 있어 코드 규칙과 기계 대조를 쓰기 좋습니다. 다만 표의 칸 구성이 회사마다 달라, 삼성화재에 맞춰 만든 지금 표 추출기는 다른 회사에서 급부 절을 찾지 못합니다. 회사를 넣기 전에 표 추출기를 넓혀야 합니다.

## 10. 공모전 관점

내세울 내용은 세 마디이고, 마디마다 증거를 하나씩 붙입니다.

| 메시지 | 보여 줄 증거 |
| --- | --- |
| 최신 기술 시도 | 2026-11-11에 나온 판정 전용 모델을 실제 업무 흐름에 넣어 돌린 기록 |
| 적재적소 | 작업별 모델 배정표(6.1, 초기 적재와 개정 운영의 구분 포함)와 "왜 여기에 이 도구, 이 모델인가"에 대한 한 줄 답 |
| 안전장치 | 정답셋으로 맞춘 판정 구간, 사람 검토 분기, 예비 경로, 화면에 공개되는 반려·재추출 기록, 문서에 없는 값을 지어내지 않고 멈춘 기록 |

- 판정 모델과 지식그래프를 하나의 흐름으로 묶습니다. 판정 모델이 그래프에 들어갈 관계를 걸러 주고, 그래프는 화면의 근거를 댑니다.
- 안전장치는 "넣었다"가 아니라 "실제로 걸러 냈다"까지 보여야 합니다. 검증 단계가 잘못된 추출값을 반려한 실제 사례를 화면 6에 둡니다.
- 문서에 없는 값은 지어내지 않습니다. 우체국 요약서에는 특약별 보험료가 없고 사업방법서의 비교표는 "x,xxx원"으로 비어 있는데, 여기서 숫자를 만들어 내지 않고 "문서에 없음"으로 멈춘 채점 기록을 화면 6에 둡니다. 정답셋의 9항목이 이를 확인하는 표본입니다.
- 가격 비교보다 문장 속 조건 차이를 앞에 세웁니다. 예: 간편심사의 기간 질문이 우체국은 입원만 묻고 한화생명과 삼성화재 새로고침은 입원 또는 수술을 묻습니다.
- 마지막은 업무 효과로 닫습니다. 기술 시연으로만 보이지 않게 하기 위함입니다.
- "최초 적용" 같은 표현은 쓰지 않습니다. 확인할 방법이 없는 주장입니다.
- 판정 전용 모델은 심사위원에게 낯선 용어일 수 있어, "글을 쓰지 않고 정해진 선택지에 확률만 매기는 모델"이라는 설명을 붙입니다.

### 10.1 성과 지표

- 정답셋 100항목 대비 추출 정확도: 한 번 추출했을 때와 검증·재추출을 거쳤을 때의 차이
- 검증 단계가 잡아낸 오류 건수, 문서에 없는 값을 묻는 항목에서 빈값으로 답한 비율
- 담보 매핑의 자동 확정 비율과 사람 검토로 넘긴 비율
- 신상품 비교표 작성 시간의 단축 폭 (기존 소요 시간은 실무에서 측정해 채움)
- 정기 주간 운영의 API 비용 0원(기존 상품의 초기 적재에는 구독 도구를 씀)

### 10.2 정답셋 구성

| 영역 | 항목 수 |
| --- | --- |
| 가입조건 | 20 |
| 보장금액·면책·감액 | 30 |
| 보험료 | 25 |
| 결합 제약 | 10 |
| 질병코드 | 15 |

100항목 가운데 10항목은 원문에 없는 내용을 묻는 표본으로 둡니다. 모델이 빈값으로 답하는지 확인하기 위함입니다.

지금 만든 정답셋은 회사별로 따로 있습니다. 위 표는 우체국 정답셋의 구성이고, 질병코드 15항목은 약관 별표가 필요해 아직 만들지 않아 지금은 85항목입니다. 한화생명은 25항목과 가입조건 24항목, 삼성화재는 두 상품 50항목(상품마다 25항목)입니다. 자세한 구성은 data/goldset/README.md에 있습니다. 정밀 비교 대상을 넓히면서 새로 넣는 회사는 회사마다 25항목 안팎을 더합니다.
