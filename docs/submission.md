# 우체국보험 상품·청약 판단 지원 앱 제출 설명 자료 (초안)

기준일은 2026-11-23입니다. 시트 수치는 2026-11-23 주간 사본(`data/snapshot/`, 2026-W48, 05:50)에서 세었고, 나머지 수치는 `docs/progress.md`, `docs/handoff.md`, `docs/planning.md`에서 가져왔습니다. 한계는 `docs/limitations.md`에 따로 모았습니다.

## 1. 소개

우체국보험 본부의 상품, 영업지원 담당자가 공개된 공시 문서와 시장 소식만으로 민영 보험사 상품과의 차이를 화면에서 바로 판단하도록 돕는 앱입니다.

- 담당자가 나이, 성별, 심사 유형 같은 조건을 고르면, 화면이 가입 적격, 간편심사 관문, 보장 조건 우열과 빈자리 특약, 특약 조합별 실제 지급액, 개정 전후 변화를 보여 줍니다. 창구 직원과 설계사에게는 A4 한 장짜리 응대 카드로 전달합니다.
- 서버와 별도 DB 없이 구글 시트, GitHub Actions, 정적 HTML 한 파일로 돌아갑니다. 개념검증 단계로 1인이 만들었습니다.

## 2. 풀려는 문제

보험사마다 특약 이름, 감액 기간, 면책기간, 가입금액 대비 지급 배수, 고지 질문이 다릅니다. 수백 쪽 공시 문서를 손으로 대조해야 하고, 차이는 가격보다 문장 속 조건에 많습니다. 간편심사 고지 질문이 한 예입니다.

- 실제 인수 여부, 손해율, 판매 시책처럼 비공개 자료가 필요한 판단은 다루지 않습니다.
- 특약별 보험료 비교와 약관 별표의 질병코드 범위 비교는 2단계로 미뤘습니다. 공시 문서에 특약 단위 보험료가 없고, 질병코드는 약관 별표를 읽어야 합니다.

## 4. 만든 것

### 자료 흐름

1. 수집: GitHub Actions가 각 사 공시실에서 상품요약서와 사업방법서를 받습니다(`scripts/fetch_disclosure.py`). 비교 대상을 넓힌 회사 가운데 한화손해보험을 뺀 회사의 접속 모듈(`src/postlife/disclosure/`)은 만들었지만 수집 스크립트에는 아직 잇지 않았고, 한화손해보험은 자동 접속 차단 때문에 사람이 문서를 내려받습니다. 시장 소식은 요일마다 기관을 나눠 검색 모델로 모읍니다(`src/postlife/collect.py`).
2. 추출: 생성 모델은 원문 글자만 옮깁니다. 만 원 환산, 개월과 일수 계산, 날짜 대조는 코드가 합니다. 삼성화재 급부표는 모델 없이 코드 규칙으로 읽습니다.
3. 검증과 분기: 코드가 원문 대조를 먼저 하고, 판정 전용 모델이 확률을 매깁니다. 0.75 이상은 확정, 0.40 이상 0.75 미만은 사람 검토입니다. 0.40 미만은 다른 모델로 다시 뽑고, 그래도 안 되면 시트에 쓰지 않습니다.
4. 저장: 검증을 거친 행만 구글 시트 정본(탭 13개)에 쓰고, 모든 단계를 `sys_작업로그`에 남깁니다.
5. 화면: 시트를 정렬된 JSON Lines 사본(`data/snapshot/`)으로 떠서 `site/index.html` 한 파일을 만듭니다. 외부 요청이 없어 파일을 직접 열어도 동작합니다.

- 해설 글: 화면마다 결론 한 줄, 읽는 법, 이유, 실무 유의점, 출처가 붙습니다. 글 속 숫자와 이름은 모두 변수 자리이고, 화면이 고른 조건의 값을 끼웁니다. 변수 밖에 숫자가 있는 글은 빌드에서 버립니다. 화면 1 맨 위의 주간 요약은 아직 모델이 아니라 코드가 집계한 것이고, 화면에도 그렇게 표시합니다.
- 응대 카드: A4 세로 한 장으로 나오고, 맨 위에 대외 배포 금지 표식을 고정합니다.

## 5. AI 도구와 에이전트를 어떻게 썼는가

### 판정 전용 모델을 검증기로

- `gemini-decision-1`은 2026-11-11에 나온 판정 전용 모델입니다. 글을 쓰지 않고 정해진 선택지(2~255개)에 확률만 매기며, 출력 토큰이 0이고 한 번에 1,000문항까지 받습니다.
- 이 모델을 추출값 정합성 채점, 표준담보 매핑, 시장 소식 선별, 중복 소식 병합에 넣었습니다.
- 문항 짜는 법은 실제 결과를 보고 고쳤습니다. 면책 조건을 진술의 참 거짓으로 물으면 맞는 줄도 0.5~0.8에 머물렀습니다. "조건 있음 / 없음" 가운데 고르게 하자 맞는 값은 0.94 이상, 뒤집은 값은 0.06 이하로 갈렸습니다.

### 제미나이: 추출기와 따로 보는 교차 확인

- Claude Code로 옮기기 전 단계에서는 제미나이 웹에 사람이 요청문과 첨부를 넣어 답을 받았습니다. 정답셋(우체국 85항목, 한화생명 25항목, 삼성화재 50항목), 우체국 직전 개정 상품 급부 90줄 교차 확인, 삼성화재 급부 독립 구조화, 한화 추출 결과 표본 대조, 매핑 대기 388종류 분류 의견, 추출과 검증 코드 검토 26건이 여기에 속합니다.
- Claude Code로 넘어온 뒤에는 구독 패널(`gemini-sub` 스킬)로 넘겼습니다. 한화생명 가입조건 정답셋 24항목, 화면 해설 글 틀과 화면 1 구성 지적, 응대 카드 구성안, 수집 스크립트와 배포 워크플로 검토, 이 문서의 초안이 여기에 속합니다. 그 뒤로 비교 대상 회사의 웹 조사, 기획서 개정 초안, 표준담보 사전 확장안 검토, 화면 코드 검토, 글자가 그림으로 든 문서의 판독도 패널에 넘겼습니다.
- 삼성화재 가입조건과 결합 제약의 독립 구조화도 패널에서 했습니다(질문 12개). 가입조건은 THE FIT 8종 특약 279개와 새로고침 7종 특약 244개의 답을 원문 줄과 기계로 맞췄고 모두 일치했습니다. 패널에서도 질문마다 사람이 직접 입력해야 답이 옵니다.
- 제미나이 모델도 일의 성격에 따라 골랐습니다. 기계로 전부 대조할 수 있는 표 구조화는 가벼운 모델(하이드로젠)로 낮춰도 대조 결과가 같았고, 판단이 들어가는 결합 제약 분류는 한 단계 위 모델(네온)에, 검토와 초안은 가장 위 모델(카본)에 맡겼습니다.
- 요청문 틀은 `docs/gemini_requests/`, 받은 결과는 `data/crosscheck/`와 `data/goldset/`에 있습니다.
- 검수 기준: 제미나이의 지적과 결과는 Claude가 직접 확인해 동의한 것만 반영합니다. 근거 문구와 숫자는 원문의 그 쪽에 있는지 기계로 대조하고, 코드 지적은 재현되는 것만 고칩니다. 확인하지 못한 것은 미확인으로 남깁니다.

### Claude Code와 서브에이전트

- 메인 세션은 작업 순서와 범위를 정하고, 위임 결과를 시험, 재현, 원문 대조로 검수해 커밋합니다. 아끼려는 것은 메인 세션이 쓰는 최상위 모델의 사용량입니다.
- Claude Code로 넘어온 뒤 처음 띄운 구현 에이전트 하나는 모델을 지정하지 않았습니다. 그래서 메인 세션과 같은 최상위 모델, 곧 가장 비싼 모델로 돌았습니다.
- 이 일을 보고 기준을 세워 `CLAUDE.md`에 적었습니다. 서브에이전트는 모델을 항상 명시하고, 구현과 수정은 opus, 점검은 sonnet, 기계 점검은 haiku에 맡기며, 값이 정해진 기계적 수정은 에이전트 없이 직접 합니다.
- 기준을 세운 직후에는 구현과 수정과 문서 다듬기를 opus 에이전트 셋에, 질문 자료 준비를 sonnet 에이전트 하나에 맡겼고, haiku는 쓰지 않았습니다. 질문을 차례로 넣고 답을 기계로 대조하는 반복 작업은 에이전트 없이 스크립트로 돌렸습니다.
- 비교 대상을 넓힐 때는 DB손해보험 하나로 공시 접속 모듈을 먼저 만들어 검수한 뒤, 나머지 16개 회사를 워크플로로 한꺼번에 돌렸습니다. 회사마다 opus 에이전트가 공시실 요청을 조사해 접속 모듈과 시험을 만들고 대표 상품 두 개의 요약서와 사업방법서를 받았고, sonnet 에이전트가 그 모듈로 실제 호출을 해 받아 둔 파일과 해시를 대조했습니다. 메인 세션은 전체 시험(579개 통과), 바뀐 파일이 회사별 모듈과 시험뿐인지, 받은 문서 58개가 모두 PDF이고 쪽수가 보고와 같은지를 직접 확인했습니다.
- 16개 회사 가운데 15곳은 로그인이나 토큰 없이 문서를 받았습니다. 한화손해보험은 상품 목록 요청이 자동 접속 차단에 걸렸는데, 차단을 우회하지 않기로 해 접속 모듈을 만들지 않았고 이 회사 문서는 사람이 공시실에서 내려받습니다.
- 에이전트의 완료 보고는 그대로 옮기지 않습니다. 예를 들어 화면 1, 해설 글, 응대 카드는 opus 에이전트가 구현했고, 메인 세션이 시험, 빌드, 브라우저 점검을 다시 돌리고 화면 사진과 카드 PDF를 직접 열어 검수했습니다.
- Claude Code로 옮기기 전 대화 세션에서도 공시실 조사, 화면 구현, PDF 표 추출 모듈과 문구 규칙 작성, 한화 검토 줄 원문 대조, 코드 검토 지적의 재현과 수정을 서브에이전트에 맡겼습니다. 결과는 시험과 원문 대조로 검수했습니다.

### 글자가 그림으로 든 문서: 두 모델이 따로 읽고 견주기

- 미래에셋생명 요약서는 본문 글자가 쪽마다 수백 개의 작은 그림으로 들어 있어 글자를 풀 수 없습니다. 쪽 그림을 제미나이 구독 패널과 sonnet 에이전트가 따로 읽게 하고, 코드로 견줘 어긋난 줄만 원본에서 확대해 Claude가 직접 보고 판정해 두 요약서 308쪽(공백을 뺀 314,492자)을 확정했습니다. 지급률과 금액은 두 판독이 한 군데도 어긋나지 않았습니다(`docs/progress.md` "기획서 개정, 한화손해보험 조사, 그림으로 된 문서의 글자 옮기기 시험").
- 같은 판독을 되풀이해서는 오류가 잡히지 않았습니다. 제미나이가 같은 쪽을 그림과 PDF로 두 번 읽은 결과는 틀린 곳까지 글자 그대로 같았고, sonnet 에이전트를 새로 띄워 다시 읽혀도 20쪽 가운데 9쪽에서 첫 판독과 같은 식으로 틀렸습니다. 그래서 남은 문서는 sonnet과 opus가 한 번씩 읽습니다. sonnet이 틀렸던 20쪽을 opus가 다시 읽은 결과는 25,048자가 확정본과 한 글자도 다르지 않았고(공백과 따옴표 종류 제외), Claude가 처음 판정할 때 잘못 고친 한 곳도 이때 찾아 원문대로 되돌렸습니다.
- 로컬 OCR(tesseract)은 글자를 풀 수 있는 대조용 쪽에서 1,123자 가운데 100자를 빠뜨리고 110자를 잘못 넣어, 값에는 쓰지 않고 급부 표가 있는 쪽을 찾는 데만 씁니다.

### 사람이 정하는 것

- 담당자 탭 4개(표준담보 사전, 담보 매핑, 기준값, 표준질병군)의 값과 스키마 변경은 사람이 정합니다. 자동 확정 기준을 바꾸거나 사전에 줄을 더하는 일도 사용자 말이 있어야 합니다.
- 판정 경계값은 모두 기준값 탭에 두어, 코드를 고치지 않고 담당자가 조정할 수 있습니다.

## 6. 안전장치가 실제로 걸러 낸 사례

**틀린 추출값을 확정하지 않고 사람 검토로 넘겼습니다.**
- 우체국 통합건강보험 2504 첫 실행에서 재추출 모델이 재해장해생활자금의 장해지급률 구간 하나를 빠뜨리고 금액을 한 칸씩 밀려 적었습니다. 판정 확률이 0.07과 0.71이라 확정되지 않고 사람 검토로 갔습니다. 틀린 값이 확정된 줄은 없습니다.
- 표적항암약물허가치료특약은 가벼운 모델 둘 다 1,000만 원을 지급액과 감액 양쪽에 적었습니다. 코드 대조가 이를 잡아 상위 모델로 넘겼고, 2,000만 원(1년 미만 1,000만 원)으로 바로잡혔습니다.
- 결합 제약을 묶어서 물으면 잘못 끼어든 특약 2개가 0.80으로 통과했습니다. 특약마다 따로 묻자 0.42와 0.47로 걸렸습니다.

**문서에 없는 값을 지어내지 않았습니다.**
- 우체국 정답셋에서 문서에 없는 급부 2개를 묻는 항목에 추출기는 행을 만들지 않았습니다. 문서에 없는 배타 제약을 묻는 항목도 같았습니다.
- 특약 가입 한도가 공시 문서에 없는 한화생명 종형은 화면이 최대 가입 기준 지급액과 우열 판정을 만들지 않습니다.
- 첫 실제 수집에서 정형화된 소식 27건 가운데 수집 구간 밖 23건을 코드의 날짜 확인이 버렸습니다.

**교차 확인이 추출의 축약과 원문 자체의 오류를 찾았습니다.**
- 제미나이가 우체국 직전 개정 상품의 급부 90줄을 원문만 보고 다시 확인해 16줄을 짚었습니다. 지급 한도 문구가 줄어든 9줄, 장해지급률 배수가 빠진 2줄, 주석 예외 4줄이 맞는 지적이었고 1줄은 문제가 없었습니다. 지시문과 대조 규칙을 고쳐 다시 뽑자, 우체국 급부 383행의 매핑 대기가 44행에서 22행으로 줄었습니다.
- 삼성화재는 규칙 추출과 제미나이의 독립 구조화를 줄마다 맞췄습니다. THE FIT은 339줄 중 337줄, 새로고침은 342줄 중 334줄이 일치했습니다. 다른 줄은 규칙이 스스로 확신 없음으로 표시한 줄이거나 괄호 표기 차이였습니다.
- 제미나이가 "확인 필요"로 적은 곳은 요약서 원문의 오류였습니다. 새로고침 105쪽은 본문과 주석의 한도가 엇갈리고, 140쪽은 주석의 담보명이 잘못 적혀 있습니다.

**코드 검토와 결과 파일 보존이 자료 유실을 막았습니다.**

**2026-11-19 제미나이 검토가 걸러 낸 것**

### 향후 계획: 견주는 범위 넓히기

지금의 범위는 생명보험과 손해보험의 대형사, 그리고 건강보험(종합형, 간편형)입니다. 아래는 범위 밖에 둔 것이고, 실무자 사용검증의 의견을 받아 넣을지와 순서를 정합니다.

- 회사를 채우는 순서: 스무 곳을 같은 무게로 채우지 않고 실무자가 실제로 견주는 회사부터 넣습니다. 교보생명(생명보험 대형 3사를 채움), 현대해상과 DB손해보험과 KB손해보험(손해보험 대형사), NH농협생명과 NH농협손해보험(창구 기반이라 고객층이 겹침)의 순서이고, 나머지는 사용검증 의견을 보고 정합니다(2026-11-24 결정).
- 가입 조건을 맞춘 비교: 실무자 한 명이 비교 기준이 회사마다 달라(특약마다 필수 가입금액이 다르고, 회사마다 필수로 가입해야 하는 특약과 함께 가입해야 하는 특약이 다름) 같은 보장의 비교가 어렵다고 답했습니다. 지금 특약 가입조건(544행)과 결합 제약(79건)은 우체국만 적재했고 타사는 주계약 가입조건만 있습니다. 타사의 특약 가입조건과 결합 제약을 적재해 가입 조건을 맞춘 비교로 넓힙니다. 회사 확대와 이 일 가운데 무엇을 먼저 할지는 제출 뒤에 정합니다.
- 공제(새마을금고, 신협, 수협): 판매 방식과 고객층이 우체국보험과 겹칠 것으로 보는 곳인데 지금 대상에 없습니다. 공시 문서를 같은 방식으로 받을 수 있는지부터 확인해야 하고, 아직 확인하지 않았습니다.
- 다른 상품 종류: 암보험 단독 상품, 치매와 간병 보험, 어린이보험은 다루지 않습니다. 넣으려면 표준담보 사전(지금은 암, 뇌, 심장, 입원과 수술)을 먼저 넓혀야 합니다.
- 사용검증: 영업 기획과 분석 담당 실무자에게 과제 여섯과 의견 양식으로 받습니다(`docs/validation/`). 양식에서 "견주고 싶은데 빠져 있는 회사나 상품"을 물어 위 후보의 우선순위를 정합니다.
